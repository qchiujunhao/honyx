# Honyx Design

## 1. Purpose

Coding agents can solve open-ended scientific analyses efficiently, but their
successful work often remains entangled with a conversation, an exploratory
workspace, implicit decisions, and one-off code. Honyx wraps existing agents and
changes the completion condition:

> An analysis is complete only when its final method has become a portable,
> independently executable, and verified scientific object.

Honyx is not a new coding agent, workflow language, notebook system, or execution
platform. Codex, Claude Code, and future agents remain responsible for scientific
reasoning and implementation. Honyx supplies the protocol, skills, package
contract, verification evidence, and completion gate.

The reproducible object is the final analysis, not the agent's failed attempts,
tool-reading history, or hidden reasoning.

## 2. Design principles

1. **Method over trace.** Preserve result-affecting scientific operations and
   decisions, not the agent's exploratory transcript.
2. **Freedom before convergence.** Permit arbitrary code and interactive
   exploration; impose structure on the final deliverable.
3. **Evidence over declaration.** An agent may author a package but cannot grant
   its own verification status.
4. **Portable source of truth.** The package must remain useful without a Honyx
   website or the originating agent vendor.
5. **Human and agent legibility.** Natural-language method documentation and a
   machine contract describe the same analysis.
6. **Method and execution are distinct.** Scientific semantics must not be
   confused with a particular language, library, container, or backend.
7. **Verification is multidimensional.** Avoid an undefined green
   “reproducible” badge.
8. **Models improve; protocols persist.** Keep vendor adapters thin so stronger
   models improve Honyx without replacing its core.

## 3. Canonical object model

### Method

A versioned scientific procedure independent of a particular dataset or
implementation. It defines the question, input roles, result-affecting steps,
parameters, assumptions, output semantics, and method invariants.

### Implementation

An executable realization of a Method. Implementations may use Python, R,
shell, notebooks converted to canonical programs, Galaxy, or other backends.
Multiple implementations can conform to one Method.

### Run

One application of an Implementation to declared inputs and parameter values. A
Run produces concrete outputs and scientific claims.

### Verification

Evidence generated by a verifier, not an author assertion. It records the
verification policy, isolated workspace, command outcome, output comparisons,
method review, and any unresolved limitations.

The long-term relationship is:

```text
Method
├── Implementation A
│   ├── Run 1
│   │   ├── Regeneration verification
│   │   └── Agent-transfer verification
│   └── Run 2
└── Implementation B
    └── Independent conformance verification
```

## 4. System architecture

```text
Codex adapter     Claude adapter     Future adapter
      └────────────────┬──────────────────┘
                       │
              Agent supervision protocol
                       │
     ┌─────────────────┼──────────────────┐
     │                 │                  │
Method compiler   Verification engine   Repair loop
     │                 │                  │
     └─────────────────┼──────────────────┘
                       │
              Portable Honyx package
                       │
       ┌───────────────┼────────────────┐
       │               │                │
 Local execution   Agent handoff   Registry/publisher
```

### Agent supervision protocol

Vendor integrations implement stable lifecycle actions rather than embedding
Honyx semantics in vendor-specific hooks:

- `checkpoint`: update the living model of the method;
- `finalize`: separate the canonical analysis from exploration;
- `audit`: search for implicit or contradictory method decisions;
- `verify`: request deterministic regeneration;
- `repair`: correct a package from bounded failure evidence;
- `reproduce`: hand the package to a context-free agent;
- `publish`: distribute the package and verification evidence;
- `derive`: create a versioned method variation.

CLI wrappers, Codex skills, MCP tools, and Claude Code hooks are adapters to this
protocol, not the protocol itself.

## 5. Agent roles and skills

### Author

Complete the scientific analysis and create the canonical package. Remove failed
experiments from the final method without hiding decisions that affect results.

### Method reviewer

Look for counterexamples to completeness: undeclared filtering, result-dependent
thresholds, manual inspection, ambiguous input roles, external database drift,
and disagreement between method prose and implementation.

### Deterministic verifier

Validate paths and schemas, construct an allowlisted workspace, hide reference
outputs, execute the canonical entrypoint, and compare regenerated outputs. This
role is code, not a language model.

### Reproducer

Receive no originating conversation. Use only the package and permitted inputs
to understand and execute the analysis, then report missing information without
silently repairing the claimed method.

### Repairer

Receive bounded failure evidence and correct the package without changing the
scientific method or reported conclusion merely to make verification pass.

The first plugin exposes these roles through one coordinating skill. Separate
skills can be introduced when observed use shows that independent triggering and
context are beneficial.

## 6. Completion lifecycle

```text
Exploring
  → Answer ready
  → Method finalizing
  → Package structurally valid
  → Clean regeneration attempted
  → Verified or repair required
  → Context-free handoff attempted
  → Transferable or incomplete
  → Published or retained locally
```

An agent's statement that it is finished never advances a verification state.
Only verifier evidence does.

## 7. Verification dimensions

Honyx reports independent dimensions instead of one universal score:

| Dimension | Evidence |
| --- | --- |
| Package-valid | Contract and path checks pass |
| Executable | Canonical entrypoint exits successfully |
| Regenerable | Declared outputs are created from allowlisted inputs/resources |
| Output-equivalent | Regenerated outputs satisfy declared comparisons |
| Environment-resolved | A declared environment can be reconstructed |
| Agent-transferable | A context-free agent can understand and execute the package |
| Method-conformant | Implementation matches the declared scientific semantics |
| Independently implemented | A different implementation produces equivalent conclusions |
| Reusable | The Method succeeds on compatible new inputs |
| Human-reviewed | A named human has reviewed the scientific method |

The implemented v0 verifies package validity, execution, regeneration, and
output equivalence in the current environment. It must not claim the other
dimensions.

## 8. Verification integrity

The verifier must prevent accidental circular verification:

- never expose reference outputs before execution;
- copy only declared inputs and implementation resources;
- treat declared scientific input bytes as immutable verification evidence;
- require an explicitly new Run when scientifically justified inputs change;
- reject absolute paths and parent-directory traversal;
- reject overlap between outputs and inputs/resources;
- create the output directory only through the analysis entrypoint;
- keep author claims separate from verifier evidence;
- do not allow package code to redefine the verifier;
- record limitations when operating without a process or network sandbox.

No general verifier can prove that arbitrary code has not hard-coded an answer.
Model review, input perturbation, method tests, and independent implementation
provide progressively stronger evidence. Honyx must describe the evidence it has
rather than overstate certainty.

## 9. Package layers

The portable package contains four separable planes:

1. **Method plane:** method identity, documentation, semantics, and assumptions.
2. **Implementation plane:** code, resources, entrypoint, and environment
   declaration.
3. **Run plane:** concrete inputs, parameters, outputs, and result narrative.
4. **Evidence plane:** reports produced by independent verifiers and reviewers.

The v0 `honyx.json` contract intentionally represents a small executable subset.
It will evolve through versioned schemas and migration, not unversioned field
mutation.

## 10. Method evolution

Honyx must eventually distinguish:

- an implementation-only patch;
- an environment refresh;
- a new Run with different inputs or configurable parameters;
- a backward-compatible Method extension;
- a semantic Method revision;
- a derived Method;
- an independent reproduction.

Agents may propose the classification, but semantic changes require explicit
evidence and cannot be hidden as implementation repairs.

## 11. Relationship to Galaxy

Galaxy obtains reproducibility by constraining execution into structured tools,
parameters, datasets, and lineage from the beginning. Honyx permits open coding
and establishes structure at completion. Galaxy therefore provides stronger
execution provenance today; Honyx aims at broader, method-level portability
across languages, agents, and backends.

Galaxy can remain an execution backend, export target, or independent verifier
for Honyx Methods. Honyx does not need to reproduce Galaxy's public compute,
curated tools, reference data, or job scheduler.

## 12. Implementation sequence

1. Versioned package contract and deterministic clean verifier.
2. Authoring skill, adversarial method review, and bounded repair prompts.
3. Environment resolvers and stronger local isolation.
4. Context-free reproduction across agent vendors.
5. Living Method checkpoints and lifecycle adapters.
6. Method semantics, conformance tests, and alternative implementations.
7. Static publication, registry, version graph, and hosted verification.

This ordering limits implementation risk without narrowing the long-term design.
